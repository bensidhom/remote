# Bridgette planning mode vs raw SQL: 100-question comparison

The same versioned SNBI question bank and the same database copy were used for both runs. The bank expects 81 direct answers, 14 clarifications, and 5 abstentions. A returned answer is counted as coverage, not automatically as correctness.

## Result

Raw SQL is more complete by direct-answer coverage, but planning mode is much safer and more semantically reliable. Planning should remain the production default; raw SQL should only be used behind narrow reviewed templates and post-query validation.

| Metric | Planning mode | Raw SQL mode |
|---|---:|---:|
| Direct answers across all 100 | 49 | 88 |
| Expected-answer cases directly answered | 48/81 (59.3%) | 70/81 (86.4%) |
| Correct clarification/abstention behavior | 18/19 (94.7%) | 1/19 (5.3%) |
| Bank behavior match | 66/100 | 71/100 |
| Total time | 316.799s | 292.969s |
| Mean time/question | 3.168s | 2.930s |

The raw SQL behavior-match total is slightly higher only because its additional direct answers outnumber its safe-behavior failures. It is not a 71% factual-correctness score. In the 19 cases that deliberately require clarification or abstention, planning handled 18 safely; raw SQL handled only 1 safely.

## High-impact audited defects

- Raw SQL confused code letters with meanings: `approach_roadway_alignment = 'G'` became Good bridge condition, and `= 'F'` became Fair condition.
- Raw SQL fabricated crash evidence with `0 AS crash_count`, then claimed the bridges had zero crashes.
- Raw SQL converted a non-toll inventory code into a current toll price of $0, although no toll-price field exists.
- Raw SQL silently invented definitions for ambiguous phrases such as “bad condition” and “NHS bridges.”
- Planning dropped the Bergen County filter in one concrete-deck query, proving that validated plans still need intent-to-plan constraint checks.
- Planning also substituted the concrete-deck metric for a reinforced-concrete substructure question; unsupported reviewed concepts must be blocked before plan generation.

## Recommendation

Keep planning mode as the production default. Raw SQL has higher direct-answer coverage and slightly lower latency, but it must not be enabled as an unrestricted fallback because the paired run exposed silent field substitutions, ambiguous-term assumptions, and fabricated evidence. Improve planning coverage and add narrowly reviewed deterministic fallbacks for validated intents.

The priority is to raise planning coverage from 48/81 without weakening its safe handling. The best path is to fix plan-generation retries/timeouts, verify every requested constraint survives into the canonical plan, expand reviewed metrics/resources, and add deterministic fallback templates only for intents whose field mappings and definitions are validated.
